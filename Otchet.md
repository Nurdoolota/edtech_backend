3 Описание программного продукта, разработанного за период практики

3.1 Общая характеристика платформы

В период прохождения практики проводилась доработка информационной платформы для изучения английского языка в IT-сфере на основе алгоритмов микрообучения. Платформа реализована в виде распределённой системы, построенной по микросервисной архитектуре, и включает в себя пять серверных компонентов (сервисов) и клиентское веб-приложение типа SPA (Single Page Application).

Серверная часть разработана на языке Java с использованием фреймворка Spring Boot версии 3.x. В качестве системы управления базами данных используется PostgreSQL; управление схемой осуществляется средствами миграционного инструмента Flyway. Клиентская часть реализована на фреймворке React (TypeScript) с применением библиотек TanStack Query и Tailwind CSS. Взаимодействие между клиентом и серверной частью осуществляется по протоколу HTTP через единую точку входа — API Gateway.

3.2 Описание выполненных доработок

3.2.1 Исправление маршрутизации запросов к ИИ-сервису

В ходе анализа программной платформы были выявлены ошибки в конфигурации API Gateway, приводившие к недоступности эндпоинтов ИИ-сервиса для клиентских запросов. В частности, отсутствовали публичные маршруты для потока восстановления пароля, а health-чек ИИ-сервиса не был доступен через шлюз.

В процессе доработки в конфигурацию gateway-service были внесены следующие изменения:
— добавлены публичные маршруты (без требования JWT-токена) для эндпоинтов /api/v1/auth/forgot-password и /api/v1/auth/reset-password;
— добавлен проксируемый маршрут для health-чека ИИ-сервиса (/api/v1/ai/health);
— реализованы отдельные бакеты ограничения частоты запросов (rate limiting) для чувствительных эндпоинтов аутентификации с более жёсткими лимитами по сравнению с глобальными настройками.

3.2.2 Доработка структуры учебных курсов

Исходная реализация content-service поддерживала только двухуровневую структуру «курс — задание». Для обеспечения более гибкой организации учебного материала была проведена следующая доработка:

— реализован полноценный CRUD для сущностей «Топик» (Topic) и «Урок» (Lesson) с поддержкой изменения порядка элементов через эндпоинт PATCH /reorder;
— добавлено управление блоками урока (Lesson Blocks) с типами TEXT, IMAGE, VIDEO, AUDIO и серверной валидацией JSONB-содержимого по типу блока;
— реализован эндпоинт GET /api/v1/content/courses/{id}/tree, возвращающий полное дерево курса «курс → топики → уроки → задания» за один запрос, что существенно снижает количество HTTP-запросов со стороны клиента.

В результате иерархия учебного контента приобрела трёхуровневый вид: курс — топик — урок — блок/задание, что соответствует принципам микрообучения.

3.2.3 Просмотр содержимого курсов и тем преподавателем

Для обеспечения удобного контроля учебного процесса со стороны преподавателя были реализованы следующие возможности:

— эндпоинт GET /api/v1/content/courses/{id}/tree предоставляет полную структуру курса в иерархическом виде;
— эндпоинт GET /api/v1/content/courses/{id}/stats возвращает статистику курса: количество зачисленных студентов, средний балл и процент завершения;
— реализован эндпоинт GET /api/v1/content/lessons/{id}/available-tasks, который с учётом индивидуального прогресса студента возвращает только разблокированные на данный момент задания урока.

3.2.4 Механизм задания последовательности выполнения заданий

В рамках реализации алгоритмов микрообучения в learning-service был внедрён механизм управления порядком прохождения заданий. Поддерживаются два режима:

— SEQUENTIAL — строгая последовательность: студент не может перейти к следующему заданию, пока не выполнено текущее;
— PREREQUISITE — зависимость по предшественникам: задание разблокируется только при наличии засчитанных результатов по всем заданиям из списка prerequisite_task_ids.

При попытке обратиться к заблокированному заданию система возвращает ответ 403 Forbidden с поясняющим сообщением. Для предотвращения циклических зависимостей при сохранении задания в content-service выполняется проверка алгоритмом обхода в глубину (DFS); при обнаружении цикла возвращается ошибка 422 Unprocessable Entity.

Дополнительно в структуру результата (TaskResult) введено разделение полей оценки: ai_score фиксирует оценку, выставленную ИИ-сервисом, а teacher_score — оценку, присвоенную преподавателем при ручной валидации.

3.2.5 Управление списком студентов и учебными группами

Для удобства работы преподавателя с контингентом обучающихся в content-service были реализованы следующие возможности:

— эндпоинт GET /api/v1/content/students — список студентов с пагинацией и поиском по имени или адресу электронной почты;
— эндпоинт GET /api/v1/content/students/{id} — детальная карточка студента с перечнем его групп и прогрессом по курсам;
— эндпоинт POST /api/v1/content/groups/{id}/students/bulk — массовое добавление студентов в группу: принимает список идентификаторов пользователей, игнорирует дубликаты и возвращает количество фактически добавленных обучающихся.

3.2.6 Загрузка и выгрузка базы знаний

Для обеспечения удобного переноса и обновления учебного контента реализован механизм импорта и экспорта курсов:

— экспорт: эндпоинт GET /api/v1/content/courses/{id}/export формирует ZIP-архив, содержащий JSON-манифест с полной структурой курса (топики, уроки, блоки, задания) и связанные медиафайлы;
— импорт: эндпоинт POST /api/v1/content/courses/import принимает ZIP-архив, разворачивает его содержимое, восстанавливает структуру курса в базе данных и возвращает идентификатор созданного курса.

Помимо этого, реализован прокси-эндпоинт POST /api/v1/content/ai/generate, позволяющий преподавателю сформировать текст задания с помощью языковой модели прямо из интерфейса редактора курса.

3.2.7 Восстановление пароля по электронной почте

В auth-service реализован двухэтапный поток восстановления доступа к учётной записи:

1. Пользователь обращается к эндпоинту POST /api/v1/auth/forgot-password, указывая адрес электронной почты. Система генерирует одноразовый токен со временем жизни 15 минут и отправляет письмо со ссылкой для сброса пароля.
2. Пользователь переходит по ссылке и направляет запрос к POST /api/v1/auth/reset-password, передавая токен и новый пароль. Система проверяет актуальность токена, применяет новый хэш пароля (BCrypt) и инвалидирует использованный токен.

Для отправки почтовых сообщений разработан переключаемый компонент EmailService с двумя режимами работы: SMTP — реальная отправка через сервер исходящей почты, LOG — вывод содержимого письма в журнал приложения (используется в среде разработки). Режим задаётся переменной окружения EMAIL_MODE без изменения исходного кода.

Письма формируются по шаблонам Thymeleaf, что обеспечивает единообразное HTML-оформление уведомлений. Аналогичный механизм применяется для подтверждения смены адреса электронной почты (эндпоинты /change-email/request и /change-email/confirm).

3.2.8 Профиль пользователя

Для всех зарегистрированных пользователей реализован пользовательский профиль со следующими возможностями:

— просмотр персональной информации через эндпоинт GET /api/v1/auth/me (имя, фамилия, адрес электронной почты, роль, ссылка на аватар);
— редактирование имени и фамилии через эндпоинт PATCH /api/v1/auth/me;
— загрузка фотографии профиля (аватара) через эндпоинт POST /api/v1/auth/me/avatar с поддержкой multipart/form-data; изображение сохраняется на сервере и доступно по статическому URL;
— смена пароля через эндпоинт POST /api/v1/auth/change-password с проверкой текущего пароля;
— деактивация учётной записи через эндпоинт DELETE /api/v1/auth/me.

3.2.9 Доработка ИИ-сервиса

В период практики функциональность ai-service была существенно расширена:

— реализован health-check эндпоинт GET /internal/ai/health, выполняющий ping-запрос к LLM-провайдеру и возвращающий статус доступности сервиса и измеренную латентность;
— разработан компонент AiRetryExecutor, обеспечивающий автоматический повтор запроса к языковой модели при временных сбоях провайдера с экспоненциальной задержкой между попытками;
— разработан компонент JsonRepairer для восстановления частично повреждённых JSON-ответов модели: удаление markdown-обёрток (```json ... ```), исправление незакрытых структур;
— реализован журнал вызовов AI: каждый запрос к языковой модели фиксируется во внутреннем хранилище (POST /internal/ai/log); история доступна через GET /internal/ai/log с фильтрацией и для администратора через прокси-эндпоинт GET /api/v1/admin/ai-log;
— добавлен эндпоинт генерации учебного контента POST /internal/ai/generate, позволяющий формировать тексты заданий на основе шаблонов и пользовательских параметров.

3.3 Тестирование

По завершении каждого этапа разработки проводилось тестирование реализованного функционала. Тестирование включало:

— модульные тесты (unit tests) для компонентов KeyBasedChecker, AiBasedChecker, LearningService и AiEvaluationService, покрывающие основные сценарии проверки ответов и парсинга JSON;
— интеграционное тестирование REST API с использованием MockMvc и утилиты Postman для проверки корректности HTTP-кодов ответов, структуры тела ответа и поведения при граничных условиях;
— проверку негативных сценариев: попытка студента обратиться к заблокированному заданию, повторный сабмит уже валидированного результата, передача некорректного токена при сбросе пароля;
— ручную проверку сценариев восстановления пароля с реальной отправкой письма через SMTP.

Выявленные в ходе тестирования ошибки были устранены до завершения соответствующего этапа. В частности, была исправлена ошибка сериализации ответов типа FILL_BLANKS (сохранение данных в формате JSONB вместо VARCHAR), а также устранены несоответствия HTTP-кодов в content-service при операциях с группами.

Все задачи, поставленные в индивидуальном задании, выполнены в полном объёме в соответствии с утверждённым календарным планом.

1. Устранены ошибки маршрутизации запросов к ИИ-сервису, восстановлена корректная работа интеллектуального модуля платформы и обеспечена защита чувствительных эндпоинтов отдельными правилами ограничения частоты запросов.

2. Реализована трёхуровневая иерархическая структура учебного контента «курс — топик — урок — блок/задание», что позволяет преподавателю структурировать материал в соответствии с принципами микрообучения и поэтапно раскрывать тему.

3. Предоставлены инструменты преподавателя для просмотра содержимого курсов и тем: эндпоинты дерева курса и статистики, а также отображение доступных заданий с учётом индивидуального прогресса студента.

4. Внедрён механизм управления порядком прохождения заданий (режимы SEQUENTIAL и PREREQUISITE) с проверкой циклических зависимостей, что обеспечивает последовательное и логически выстроенное освоение материала.

5. Разработаны инструменты управления контингентом: список студентов с поиском, детальная карточка обучающегося и массовое добавление студентов в учебные группы.

6. Реализован механизм импорта и экспорта учебного курса в формате ZIP-архива с JSON-манифестом, значительно упрощающий перенос и обновление базы знаний платформы.

7. Внедрена функция восстановления пароля с отправкой одноразовой ссылки на электронную почту пользователя, а также функция подтверждённой смены адреса электронной почты.

8. Разработан пользовательский профиль с возможностью редактирования персональных данных, загрузки аватара и смены пароля.

9. Расширены возможности ИИ-сервиса: добавлены компоненты устойчивости (повтор запроса, восстановление JSON), журнал вызовов языковой модели и эндпоинт генерации учебного контента.

Выполненные доработки повышают педагогическую эффективность платформы, упрощают её сопровождение и расширяют возможности как для преподавателей, так и для студентов. Полученный практический опыт охватывает проектирование и реализацию REST API на Spring Boot, работу с микросервисной архитектурой, интеграцию с внешними LLM-провайдерами, а также применение инструментов тестирования и отладки серверных приложений.
